# Порядок установки пакета №1

## 1. Сохранить текущее состояние

1. Сохранить текущий GitHub-коммит и URL работающего deployment Vercel.
2. Сделать резервную копию обеих таблиц Supabase, их схемы, индексов, ограничений, политик и grants. CSV сохраняет данные, но не заменяет резервную копию схемы.
3. Сохранить список названий и собственную защищённую копию значений переменных Vercel. Не добавлять секреты в репозиторий.
4. Проверить наличие pending-постов и остановить старые автоматические/внешние запуски на время переключения.

## 2. Отдельная ветка и тестовые сервисы

Создать ветку, например `fix/auth-and-publishing`, от актуального `main`.
Распаковать архив. Загрузить **содержимое папки postai**, а не сам ZIP и не дополнительную вложенную папку, в корень репозитория этой ветки.
Все исходные изображения и ресурсы включены. `node_modules` и `dist` не нужны: Vercel создаст сборку.

Тестовую версию сначала связать с отдельной тестовой Supabase-базой, Upstash и тестовым Telegram-ботом/каналом.
Preview с production-базой и тем же Redis способен менять реальные данные и лимиты — для первой проверки его не использовать.
Тестовые Clerk-ключи должны относиться к одному и тому же приложению и instance. Пока можно сохранить текущую Development instance.

## 3. Подготовить таблицы

В SQL Editor тестовой базы выполнить `sql/01_prepare.sql`.
Эта миграция добавляет столбцы и индексы, не удаляет записи и не отключает старые политики.
В конце она показывает существующие CHECK-ограничения статуса. Если они есть, убедиться, что разрешены:
`pending`, `processing`, `publishing`, `published`, `failed`, `unknown`.
Не удалять ограничения автоматически: адаптировать точное найденное ограничение.

Старые корневые `migrate.sql` и `supabase-schema.sql` — исторические файлы исходного проекта. Для этого перехода их не выполнять.

## 4. Переменные Vercel

Build command: `npm run build`; output directory: `dist`.

| Название | Что указать |
|---|---|
| VITE_CLERK_PUBLISHABLE_KEY | Публичный pk_test_ или pk_live_ от используемой instance Clerk |
| CLERK_SECRET_KEY | Серверный ключ той же Clerk instance |
| CLERK_AUTHORIZED_PARTIES | Точные разрешённые origin через запятую, например https://postai.ink и точный тестовый URL |
| SUPABASE_URL | URL нужной Supabase-базы |
| SUPABASE_SERVICE_ROLE_KEY | Секретный legacy service_role JWT этой базы, только на сервере |
| KV_REST_API_URL | REST URL нужного Upstash Redis |
| KV_REST_API_TOKEN | Серверный REST token Upstash |
| ANTHROPIC_API_KEY | Серверный ключ Anthropic |
| ANTHROPIC_MODEL | Модель, доступная аккаунту; по умолчанию claude-sonnet-4-5, проверить живым запросом |
| TELEGRAM_BOT_TOKEN | Токен нужного бота |
| CRON_SECRET | Новый длинный случайный секрет обработчика очереди |
| VITE_SCHEDULER_CADENCE_HINT | Необязательная правдивая подсказка о частоте очереди; по умолчанию раз в сутки |

SUPABASE_ANON_KEY новый сервер больше не использует. Секреты не должны иметь префикс VITE_.
При смене публичных VITE-переменных нужна новая сборка.
Не использовать wildcard для всех vercel.app origins. Настроить и разрешённые URL в Clerk, если они требуются для тестового домена.

## 5. Старые пользователи и записи

В Clerk проверить каждого владельца и его user ID. Создать вручную проверенную таблицу соответствий email → Clerk user ID.
Для каждого соответствия заполнить отдельную копию `sql/02_link_legacy_TEMPLATE.sql`, проверить затрагиваемые строки и выполнить.
Шаблон с REPLACE_WITH… выполнять нельзя. Записи с user_id NULL сервер очереди игнорирует.

verified_at остаётся NULL намеренно. Для подтверждения канала:
1. Войти в приложение, открыть планировщик, нажать «Добавить новый канал».
2. Указать @username, нажать «Получить код».
3. Временно добавить выданный код в описание канала. Срок действия — 15 минут.
4. Добавить бота администратором с правом публикации.
5. Нажать «Проверить канал». После успешной проверки код можно убрать.

Нельзя считать канал подтверждённым только на основании совпавшего email. Публичный @username тоже не доказывает владение.

## 6. Закрыть старый доступ и проверить

После развёртывания нового сервера с service_role выполнить `sql/03_lockdown.sql` в тестовой базе.
Скрипт удаляет существующие политики обеих таблиц и отзывает права anon/authenticated; это сознательное изменение архитектуры.
Сервер остаётся привилегированным и проверяет владельца сам. Если к этим таблицам обращаются другие приложения/боты напрямую с anon-key, их нужно предварительно адаптировать.
Проверить весь сценарий ниже. Только после этого повторить подготовку, привязку, deployment и lockdown в production в согласованное окно.
Не оставлять период между развёртыванием и lockdown надолго: прежний прямой анонимный доступ до lockdown сохраняется.

## 7. Проверки перед запуском

- Без сессии GET /api/usage и личные API возвращают 401.
- С подменённым email нельзя изменить владельца или получить повышенный лимит.
- Первый успешный пост расходует 1 пробную генерацию; второй получает free_limit_reached. Старые счётчики сохраняются.
- Ошибка генерации возвращает резерв. Успешная генерация, отправка и лимит отдельно проверяются на реальных сервисах.
- Пользователь B не видит каналы A и не может их удалить или опубликовать в них.
- Без подтверждения описанием подключить чужой канал нельзя.
- Разовый пост после срабатывания очереди содержит сохранённый текст, а не новую генерацию.
- Повторный пост меняет scheduled_at на будущее; публикация без нового текста расходует генерационный лимит.
- Два запуска очереди не отправляют одну строку дважды.
- /api/publish-scheduled без правильного Bearer CRON_SECRET возвращает 401, даже с x-vercel-cron: 1.
- После lockdown запрос с anon-ключом не читает и не изменяет эти таблицы.
- robots.txt и sitemap.xml по-прежнему открываются.

## 8. Частота очереди

Оставленный cron Vercel Hobby — 09:00 UTC, один пост за запуск: максимум один пост в день.
Это технически совместимый режим для проверки, а не полноценное расписание для нескольких клиентов.
Следующим шагом выбрать внешний планировщик с секретным Authorization-заголовком или подходящий тариф.
Для каждого запуска: GET https://ВАШ-ДОМЕН/api/publish-scheduled с Authorization: Bearer СЕКРЕТ.
Не открывать URL как замену авторизации и не добавлять секрет в query string.
Изменять подсказку VITE_SCHEDULER_CADENCE_HINT только после фактического изменения частоты.

## 9. Ошибки и восстановление

- `failed`: ошибка до отправки. Проверить причину и права/квоту. Повторный запуск такого задания должен быть ручным после исправления причины.
- `unknown`: Telegram мог принять пост, но подтверждение потерялось. Сначала проверить канал; не переводить автоматически в pending.
- `processing`/`publishing`, застрявшие после завершения функции: сначала сверить с Telegram. Автоматического снятия блокировок нет намеренно.
- Если post_text уже сгенерирован и сохранён, повторная обработка использует его, не списывая генерацию снова.
- В редком случае аварийного завершения после резервирования/ответа модели, но до сохранения текста, квота может остаться занятой. Требуется ручная сверка Upstash; автоматический возврат в таком случае мог бы обойти лимит.
- Если новое приложение не запускается после lockdown, не возвращать публичные политики using(true). Безопаснее временно остановить генерацию/публикации и исправить настройки новой версии.
- Простого отката к старому deployment после lockdown недостаточно: старый код использует anon и перестанет работать. Для аварийного отката нужен отдельно проверенный серверный доступ; данные из резервной копии не восстанавливать поверх новых записей вслепую.

## 10. Что ещё требует отдельной работы

Оплата и подписки пока отсутствуют; платный лимит не выдаётся. Перенос Clerk в Production, полноценная интеграция изображений,
мониторинг очереди, удобные ручные повторы и обновление основных зависимостей — следующие этапы.
Ни один настоящий платёж и ни одна настоящая Telegram-публикация при подготовке архива не выполнялись.
